# 知识与共享业务库备份、恢复及回退

## 备份

使用同一 PostgreSQL 导出快照备份全部业务表和知识表。私有原件按该快照的 rag_objects 清单复制，并核对大小及 SHA-256；现有 assets/documents/uploads 一并复制。GC 通过 advisory lock 和 backup hold 暂停物理删除。既有资产如存在外部写入，应安排维护窗口；检测到复制过程变化即失败，不能使用不完整备份。

```sh
pnpm knowledge:backup backup /安全目录/唯一备份名 --docker-container postgres
pnpm knowledge:backup verify /安全目录/唯一备份名
```

目录必须新建；权限 0700，dump/清单/文件 0600。本地 `data/backups/` 已忽略，Docker 上下文也排除 data。完整业务库含用户凭证，备份必须额外使用受控加密存储，不能发到公共附件。配置中的秘密不自动复制；运维需在秘密管理器中单独保管 `.env` 和个人配置，并保存无秘密配置版本及镜像摘要。备份脚本异常遗留 hold 时，先确认没有备份作业再处理；过期 hold 最长 24 小时，锁随连接关闭释放。

## 恢复（不覆盖当前业务库）

1. 停止目标环境 server 和所有消费者，创建**独立空数据库**，使用相同 PG 主版本与 vector 扩展。不要复用线上 Redis 任务队列启动消费者。
2. 执行 `pnpm knowledge:backup restore /安全目录/备份名 --docker-container postgres --target-db 独立空库`。CLI 拒绝当前业务库和非空目标库；先校验 dump/文件摘要，再恢复并核对全部表计数。失败后修复原因并换新空库重试，不能向部分恢复库叠加。
3. 将备份目录中的 `data/` 恢复到**独立目标持久卷**，保持原路径和受限权限，设置应用用户所有权；CLI 恢复数据库不自动覆盖当前 data。先用只读校验程序验证原件，再启动目标 server 完成幂等迁移。
4. 核对用户/会话/生成/计费表、资料、向量、授权和检索。恢复会带回快照时有效的会话/知识 Key，按安全策略撤销或轮换；核对备份后删除记录并重新删除，避免复活已撤销资料。
5. 数据库 outbox 为事实来源；盘点 running/pending/已计费任务，清除目标隔离 Redis 中不匹配的旧任务，确认幂等恢复策略后才启动知识 worker。恢复工具不连接 Redis、不自动启动 worker、不触发模型收费。不要把生产 Redis 的旧队列直接指向恢复库。

实际演练：`pnpm check:knowledge:restore --local --docker-container postgres` 在用户指定的现有 PG 内创建独立临时数据库，恢复 75 张表、176 个文件，校验原件 hash、所有表计数、vector 0.8.6、恢复 Key、检索与撤销隔离；结束后删除该临时数据库。未新建任何容器。记录见 `tests/eval/results/restore.json`。测试复用了备份文件作为隔离原件根目录；没有覆盖原数据。

## 版本回退和保留

当前发布 schema 29；从 schema 23 升到 29 两次迁移的幂等演练通过，旧聊天、生成资产、用量未改变。迁移为增量，回退应用时先关闭知识入口和外部 Key 接入、停止知识 worker；保留知识表和私有原件，不执行反向 DROP。旧应用仅能继续原有业务，不能处理新的知识任务；schema 28 不能运行当前 worker 的 schema 29 计费写入。PG 主版本及 vector 扩展不随应用降级。

回退到部署前记录的应用镜像摘要与配置；索引 profile 回退使用 `knowledge:index` 提供的候选/激活流程，先确认模型和分词指纹兼容。涉及以后破坏性迁移时，必须使用完整恢复和流量切换，不能只回退镜像。

建议受控备份保留 30 天，并使法定/业务删除期限优先；主库删除不立即改写不可变备份。维护备份后删除台账，恢复后在开放服务前重放删除/撤销。到期安全删除 dump、清单、原件副本及其加密密钥；GC 保留窗口须覆盖最长运行中的备份窗口。清理不是恢复脚本自动执行的动作。
