4 技术路线与架构 结构合理，质量路线有风险

合理的部分

  • 前后端共用 core 里的 schema，校验规则一致。
  • 视频模型的限制写在 MarketingVideoProfile 配置里，代码不写死模型名。冻结任务按原模型恢复。
  • PG 是唯一数据来源，BullMQ 只负责投递。营销视频已有独立队列，并发可配置，按用户公平调度（F02 已修复）。
  • 上传素材使用私有签名链接，日志只记标识（F01 已修复）。
  • 没有引入通用 DAG 或多 Agent 编排。marketing_video Agent 工具白名单为空，实际是固定流程的界面，由项目 API 控制制作。两次评审一致认为当前不需要编排框架。

风险

R1 配音 质量

每一镜由视频模型单独生成配音。镜与镜之间音色不一致，口型也不准（G01）。这是成片质量的最大风险。

TTS 整段音轨→按镜切分→音频驱动 / 对口型→本地合成

保留当前方式作为"快速模式"，并写明质量边界。marketing-video.md 的"后续对口型服务候选"已经提出了这个方向。

2026-10-20 补充：R1 / R2 配音、字幕与对口型方案，包含 TTS 云服务选型、统一时间轴、改造位置和验收门槛。当前为设计建议，尚未实施。

2026-10-20 补充：TTS 配音替换模型配音实施计划（逐镜合成、试听后再付费生成视频、片段无声生成、合成时替换音轨）。只做 TTS 时人物不再开口说话，数字人口播模式体验会倒退，因此该模式应与对口型一起上线；参考视频模式当前没有旁白，可先单独上线。对口型路径（图片音频驱动或 VideoRetalk）待选定。

R2 字幕 质量

字幕由视频模型直接画进画面。模型画中文字容易出错，而且生成后改不了（G01）。建议用 TTS 时间轴生成 SRT/ASS 字幕，在本地烧录。

与 R1 共用最终配音时间轴。具体见配音与字幕方案；字幕改样式可只重新合成，改台词需更新配音和口型。

R3 参考视频分析太重 成本

链路包括 yt-dlp、抖音补丁、无头 Chromium、用户 Cookies，再加逐帧 OCR、分批视觉理解、ASR、摘要和创作，涉及 4 个模型供应商。单条视频的模型请求上限为 120 + 8 + 1 + 1 + 1 = 131 次（ANALYSIS_LIMITS），历史样例为 85 次。成本、耗时、维护和平台条款风险都高。

建议：把本地上传作为首选。用相同素材对比"快速分析"和"完整分析"，质量可接受后再降低 OCR 密度，或改用一个支持视频输入的多模态模型。

R4 同步请求 已缓解

文案和分镜生成（最长 5 分钟）在 HTTP 请求里同步执行。本次已让模型请求不随浏览器断开而中止，所以刷新不再制造未知状态。请求仍占用一个 HTTP 连接，进程重启仍会中断请求。长期仍建议改成队列任务（参考视频分析已经这样做）。审核和标题标签已接入文本操作记录（F04，2026-10-20）。

R5 保护机制的出口 部分解决

可靠性工程做得比产品验证阶段更超前：营销相关迁移已有 18 个（含 0049、0050）、回执账本、到处都有 unknown 保护。付费调用需要这些保护，两次评审都建议保留。本次已增加用户侧出口：用户确认后放弃或重提，并记录次数和时间。运营侧仍缺费用核对工具和处理时限。

R6 吞吐与公平 已缓解

2026-10-20 已增加父任务并发和每用户并发配置（默认 2 和 1），并在日志输出排队等待时间。每个视频内的片段并发也可配置（默认 2）。下一步按生产排队 P95 和内存调整默认值。在补齐核实工具之前，不要只提高并发，因为提高并发会放大模型请求、文件读取和内存占用。
