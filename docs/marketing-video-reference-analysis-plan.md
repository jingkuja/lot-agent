开发进度、配置和实际验证入口见[实现与验证说明](marketing-video-reference-analysis.md)。用户确认两个模型支持 Responses，先要求在没有测试素材时推进开发，随后提供一条小红书真链并授权本机和模型测试；下文第一、六阶段的完整验收仍保留，不能由模拟结果或单样本替代。

首版在 **lot-agent 内开发单链接视频下载与分析模块**，采用 **yt-dlp 下载、FFmpeg 抽帧、deepseek-v4.1-flash 提取画面文字、kimi-k3 理解有时间顺序的多张图片**。保留视频内容理解能力，模型输入使用图片序列；首版不接入原始视频输入，也不加入语音转写。

这条路线适合当前的“画面字幕提取与短视频营销内容摘要”。单做 OCR 只能得到文字，无法解释产品展示和画面结构；增加 Kimi 多图理解后，可以结合可见内容总结主题、展示顺序、卖点与行动号召。连续动作、声音和快速剪辑需要更密的采样或后续专项能力，不能由静态图片补全。

## 抽帧与原始视频输入的取舍

| 路线 | 可以解决什么 | 主要限制 | 本期选择 |
| --- | --- | --- | --- |
| 抽帧后只做 OCR | 提取字幕、价格、标题等可见文字 | 缺少人物、产品、场景和前后关系，不能完成内容摘要 | 不单独作为完整方案 |
| 抽帧加 OCR 加有序多图理解 | 提取文字，结合画面与时间顺序做摘要和营销结构分析 | 对采样间隙、快速动作、短暂文字与声音无直接证据 | **默认方案** |
| 将视频文件直接交给支持视频的模型 | 可能更适合动作过程、复杂剪辑与时间关系 | 效果依赖模型、内部采样和网关协议；声音能力需另验，仍可能漏字 | 留作后续对照评测 |

“需要视频理解”不等于“必须上传视频给模型”。本期的理解过程是：对有序图片及其字幕做跨帧推理，而非分别描述每张图后简单拼接。直接视频输入也不天然保证字幕更完整或成本更低，应在同一批样本上比较后决定是否增加。

若后续需求变为动作教学、运动轨迹、精确镜头运动或毫秒级事件定位，再评估原始视频输入或片段级分析；若需要真实口播，则增加 ASR。没有画面字幕的口播视频，首版仍可概括可见画面，但必须提示无法获得其讲话内容。

## 下载与分析流程

```text
单条分享链接
  → 平台识别与短链展开
  → 元信息和登录态检查
  → 受控下载到私有目录
  → 本地文件与时长校验
  → 抽帧、时间戳、变化检测
      ├─ 字幕候选帧 → DeepSeek OCR → 按时间合并文字
      └─ 场景代表帧 → Kimi 分段观察
  → Kimi 综合画面观察与字幕，生成带证据的摘要
  → 保存版本与用量 → 预览、校对、复制或选用
```

### 三平台下载适配

统一接口建议为 `resolveSource`、`downloadSource` 和 `classifyError`。保存平台、原始分享地址、规范地址、视频 ID、标题、作者、分 P 信息、采集时间、下载器版本及最终文件哈希；标题和简介属于平台元数据，不混入 OCR 原文。

| 平台 | 计划支持的输入 | 主要验证项 |
| --- | --- | --- |
| 抖音 | 视频页和 `v.douyin.com` 分享短链 | 展开后的真实 ID、Cookie 是否有效、挑战页、播放地址失效 |
| 小红书 | 视频笔记页和 `xhslink.com` 短链 | 保留必要的 `xsec_token` 等参数，区分视频与图文，校验登录态 |
| B 站 | BV 视频页和 `b23.tv` 短链 | 保留 `p` 并解析对应 `cid`，只取选定一集，检查分离媒体流和可下载清晰度 |

下载路径依次尝试平台的 yt-dlp 提取器、已验证的用户登录态，以及必要的 Playwright 页面解析。三平台都要先有真实下载样本；提取器名字存在不等于生产环境可用。抖音提取器当前包含需要新鲜 Cookie 的失败分支，见 [Douyin 提取器源码](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/tiktok.py)；其他两平台可参考 [小红书提取器](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/xiaohongshu.py) 与 [B 站提取器](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/bilibili.py)。

浏览器只负责取得用户可访问页面的元信息和媒体地址，文件仍由受控下载路径获取。平台要求登录或人工验证时返回 `AUTH_REQUIRED` 或 `CHALLENGE_REQUIRED`，保留任务，用户处理后再继续。登录态按用户和平台加密保存，禁止多用户共享一个浏览器默认上下文。

预检查平台元信息中的时长；下载后以本地探测复核。优先选满足文字清晰度的 720p 或 1080p 视频流，不为本期摘要额外下载独立音轨；若平台提供合并流，可以保留音轨但不分析。分片流的清单、分片和跳转同样执行出口限制与累计下载限额。媒体直链有有效期，失效时在有界重试内重新解析，不无限复用旧地址。

### 两组抽帧策略

不能只用场景切换或编码 I 帧：同一个镜头内字幕仍会变化。也不能只用整图相似度去重，画面基本不变时可能恰好换了价格或否定词。

**字幕候选帧**以每秒 2 帧作为试验起点，结合字幕常见区域及全图分区的灰度差分寻找变化。保留变化前后候选帧，对片头、片尾及不确定区间补采。局部区域用于发现变化，实际 OCR 默认读取清晰全帧；必要时补发带坐标映射的裁剪图，避免只看底部字幕而漏掉画面中央的价格。

**内容理解帧**按场景变化取稳定代表帧，再增加首尾和周期覆盖。相邻动作需要保留前后帧，按时间分组给 Kimi；模型看不到的区间保留为覆盖缺口。FFmpeg 的 `scdet` 可提供场景变化候选，其阈值量纲不能与 `select` 的 `scene` 参数混用，参见 [FFmpeg scdet](https://ffmpeg.org/ffmpeg-filters.html#scdet)。

所有帧保存实际源 PTS、timebase、归一到视频起点的 `ptsMs`、尺寸、源文件哈希、采样版本和帧 ID。处理旋转、容器起始偏移与可变帧率；不能按“图片序号除以假定 FPS”造时间戳。若滤镜重写时间轴，必须保留到原始时间轴的映射。

以下是开发起点，需用真实样本调整，不能视为已验证的模型容量或质量承诺：

| 限制 | 初始值 | 达到上限时 |
| --- | --- | --- |
| 视频时长 | 180 秒 | 拒绝，并说明上限 |
| 下载媒体总量 | 100 MiB，含分片 | 中止并清理未完成文件，不只依赖 Content-Length |
| 源画面与解码 | 优先最长边不超过 1920 的可用流；限制像素数和进程资源 | 不满足处理限制时明确失败 |
| 字幕基础采样 | 2 帧每秒，180 秒约 360 张候选 | 候选本地筛选，不全部自动送模型 |
| OCR 图片预算 | 最多 120 张，含补采和裁剪图 | 标记字幕覆盖不足，保留未处理区间，不能显示“完整提取” |
| Kimi 图片预算 | 最多 48 张不同代表帧，按时间分批 | 保留覆盖情况，复杂片段可返回不确定 |
| Kimi 批次 | 先试每批 6 张，新帧最多 8 批，可携带前批末帧作上下文 | 重复图片仍计入请求字节和模型预算；真实网关上限更低时缩小批次 |
| OCR 并发 | 每任务 2 个请求 | 全局与用户并发另限流，避免累计额度超支 |
| 单任务临时目录 | 512 MiB 起步 | 中止本地处理并保留已提交的结果 |

每秒 2 帧仍可能漏掉短于采样间隔的文字；字幕变化很多时，120 张预算也可能不足。界面必须展示识别覆盖状态。后续若要求“完整提取所有字幕”，需提高预算或增加本地文字检测，不能仅靠改提示词保证完整。

### OCR 与文字合并

首版优先沿用单图 OCR 请求，先保证图片与结果一一对应；网关验证多图归属稳定后再启用批量 OCR。结果分为逐帧原文和时间合并后的可读文字，两者分别保存。

合并只处理时间邻近、位置或上下文相容且文字一致的观察，不进行全片全局去重。同一句话在后文再次出现要保留；价格、单位、否定词、数量及限定条件变化时不能模糊合并。检测到重复字幕中夹有缺帧、空结果或不同文字时，保留区间边界。

文字记录保存 `frameIds`、`firstSeenMs`、`lastSeenMs`、原文和可选类型。时间表示“在这些抽样帧中观察到”，不宣称是字幕精确出现和消失时间。首版不输出精确对齐的 SRT。文本框、置信度只在提供器实际返回并通过校验时保存，禁止由后处理虚构。

用户校对价格、品牌或文字后创建修订版本；保留机器原文。综合摘要基于指定修订重跑，已成功下载及 OCR 无需重新执行。

### Kimi 多图理解

使用 Responses 的 `input[].content` 中交替排列的时间标签与图片，而不是把图片链接放进普通字符串：

```json
{
  "model": "kimi-k3",
  "store": false,
  "input": [
    {
      "role": "user",
      "content": [
        { "type": "input_text", "text": "frameId=f0001，时间=1200ms。只依据可见画面分析。" },
        { "type": "input_image", "image_url": "data:image/jpeg;base64,<图片字节>", "detail": "auto" },
        { "type": "input_text", "text": "frameId=f0002，时间=2400ms。" },
        { "type": "input_image", "image_url": "data:image/jpeg;base64,<图片字节>", "detail": "auto" }
      ]
    }
  ]
}
```

以上仅示意图片输入格式。实现另加系统约束、模型参数、用量及结束状态检查；`text.format` 等可选参数按网关实测启用，不能照搬 OCR 的 DeepSeek 专用参数给 Kimi。优先发送私有帧字节，避免为了让模型读取而公开原片和帧文件。

分两步调用：先对各时间段的图片做观察，产出主体、展示内容、事件顺序及 `frameIds`；再把分段观察、OCR 和明确标记的平台元数据送给 Kimi 综合。最后一步可用纯文本，不必重复上传全部图片。若需要复核某个价格或动作，单独补取该区间证据，并计入同一预算。

摘要 schema 至少包含 `summary`、`timeline`、`marketingPoints`、`evidenceIds` 和 `limitations`。营销要点区分钩子、卖点、展示证据和 CTA；没有证据的项允许为空。场景观察与营销作用推断分开，不能虚构口播、音效、收益或转化数据。模型只能引用服务端分配的帧与文字 ID，服务端验证所有引用、时间范围、数组数量和输出长度。

## 服务边界与数据设计

### 模块与执行环境

| 位置 | 计划职责 |
| --- | --- |
| `packages/core/src/marketing-analysis/` | 输入输出 schema、平台类型、帧与文字证据、仓储和任务接口；不引入 PG 或 Redis |
| `packages/server/src/marketing-analysis/` | 路由、repository、平台适配、下载、抽帧、OCR、理解、阶段编排及文件读取 |
| `packages/server/src/workers/media-analysis.ts` | 独立队列消费者，恢复和取消任务 |
| `packages/server/src/db/migrations/` | 追加分析表迁移并注册，编号按实现时最新迁移递增 |
| `packages/web/src/modules/marketing-video/` | 视频链接入口、进度、字幕与摘要、帧时间线、校对和历史 |
| Dockerfile、Compose、entrypoint 和环境样例 | 补下载器、Worker 角色、私有目录、资源与网络隔离 |

Worker 负责调度并在需要调用模型时获取所属用户凭证。下载器只获得该次任务所需的平台会话；解码环境无网络、无模型凭证、无数据库凭证，只挂载任务输入和输出目录。清空子进程环境变量不足以构成文件和网络隔离，部署时还需容器或等效沙箱边界。

当前 `BullmqJobQueue` 把队列名固定为 `lot-tasks`。实现时参数化队列或新增专用队列实现，并一起更新任务投递、恢复和取消路由；不能让只认识媒体任务的 Worker 与普通 Worker 竞争同一个队列，否则会取到未注册的任务类型。

### 数据对象

| 对象 | 主要字段 |
| --- | --- |
| Source | ownerId、platform、canonicalId、selectedPart、私有 mediaKey、sourceHash、durationMs、平台元数据 |
| ReferenceAnalysis | sourceId、ownerId、revision、schemaVersion、pipelineVersion、状态、预算、采样覆盖、结果快照 |
| FrameEvidence | frameId、sourceHash、原始时间信息、ptsMs、尺寸、私有 objectKey、selectionReason |
| ScreenText | textId、rawText、frameIds、firstSeenMs、lastSeenMs、可选类型、机器版本与用户修订 |
| VisualObservation | observationId、frameIds、字面观察、顺序关系、不确定性 |
| SummaryFinding | findingId、statement、evidenceIds、是否推断、引用的文字修订版本 |
| ProcessingStep | stage、batchId、inputHash、attempt、requestId、输出引用、用量、状态和错误码 |

建议新增 `marketing_reference_sources`、`marketing_reference_analyses`、`marketing_analysis_steps`。首版有上限的帧索引、OCR 与摘要可保存在 JSONB，媒体字节放私有文件存储。会话 Cookie 单独加密保存，业务记录只存不透明会话引用；含访问参数的来源地址按私密数据处理，日志脱敏。

分析可以独立存在，不要求先建营销项目。若用户选用结果，项目保存 `referenceAnalysisId`、`acceptedRevision` 和选中证据；参考视频的时间线不套用现有 15 秒生产分镜。应用到草稿须检查项目与分析版本，展示改写预览，由用户主动应用，不直接覆盖已提交的制作快照。

### 接口草案

以下保留最初接口目标；当前实现及新增预览/应用和会话接口见[实现说明](marketing-video-reference-analysis.md)。

| 接口 | 用途 |
| --- | --- |
| `POST /api/marketing-video-analyses` | 校验单链接输入及预算，事务创建分析和任务，返回 202、analysisId、taskId |
| `GET /api/marketing-video-analyses` | 当前用户分析历史，支持分页 |
| `GET /api/marketing-video-analyses/:id` | 阶段进度、覆盖情况、字幕、摘要、错误和用量 |
| `GET /api/marketing-video-analyses/:id/frames/:frameId` | 鉴权读取该用户的证据帧 |
| `POST /api/marketing-video-analyses/:id/cancel` | 设置取消标记，停止后续模型请求和本地处理 |
| `POST /api/marketing-video-analyses/:id/resume` | 从可恢复阶段继续，校验版本及未知调用状态 |
| `PATCH /api/marketing-video-analyses/:id/text` | 按 expectedRevision 保存用户校对，保留原始 OCR |
| `POST /api/marketing-video-analyses/:id/summarize` | 使用指定证据修订生成新摘要，明确本次会调用模型 |
| `DELETE /api/marketing-video-analyses/:id` | 删除分析并按引用关系清理私有文件 |

创建请求含 `clientRequestId` 以处理重复点击；用户身份由服务端认证产生，不能相信请求内的 ownerId。若启用平台登录，另提供所属用户的平台会话导入、状态及撤销接口，Cookie 不进入模型上下文。首版内测可通过安全会话导入接通；面向多用户上线前完善登录操作界面。

### 状态恢复与预算

分析状态使用 `queued`、`running`、`needs_auth`、`needs_review`、`partial`、`ready`、`failed`、`cancelled`。其中 `needs_review` 表示模型调用结果未知，需要核实；`partial` 表示存在可交付结果但部分识别或摘要未完成。

PG 为事实来源，Redis 负责投递。先在事务中保存分析、任务与不可变输入，再幂等发布；投递失败可恢复。下载、抽帧、每批 OCR、多图观察和综合分别保存检查点，任务租约与版本条件阻止两个 Worker 同时发布结果。

模型请求前保存调用意图，收到响应后保存结果和用量。任务中断后，如果请求可能已被网关处理，步骤记为 `request_unknown`，禁止队列或 SDK 自动重发付费请求；核实后由用户明确发起新尝试。已完成的批次直接复用。纯本地计算与确认未完成的下载可做有界重试。

额度检查须覆盖整项任务，不能只在每张图片前独立检查余额：按用户预留任务预算，各批次原子扣减，OCR 与 Kimi 共用总额上限。实际用量按用户、分析版本、步骤和尝试记录一次，未知费用不按零处理。取消停止后续工作，但不承诺撤销网关已接受的调用。

## 网络与文件约束

1. 输入只接受三个平台的已验证 URL 形态。展开短链时校验每次跳转，拒绝本地地址、内网 IP、云元数据地址和非 HTTP 协议；必要平台参数白名单保留，不把任意查询参数传给工具。
2. yt-dlp 和浏览器有自己的网络栈，不会自动经过 `fetchPublicBinary`。所有连接必须通过固定 DNS 解析的受限出口，连同 API、CDN 和分片一起检查；同时禁止绕过代理直连，包括 IPv6、QUIC 和其他旁路。
3. Node 使用固定可执行文件与参数数组、`shell: false`、服务端输出路径，隔离配置和插件加载。用户不能指定命令参数、文件名模板、外部下载器或脚本。
4. 网络下载与本地解码分离。禁止 FFmpeg 直接拉取任意外网清单，下载完的本地文件才进入无网络解码环境；限制挂载、CPU、内存、文件数、磁盘和运行时间。
5. 原片、帧、Cookie 与带令牌的链接不写到公开 `/static`，不在日志输出模型请求正文或密钥。模型只收到本次分析所需的图片和文字。
6. 删除、过期清理与进行中的任务、项目引用协调。建议失败临时文件及时清理，未归档原片默认保留 7 天，帧和分析保留到用户删除；具体期限作为配置并在页面说明。

## 开发顺序与完成条件

### 第一阶段 验证三平台下载与模型图片输入

每个平台先准备至少 5 条可访问的授权测试链接，覆盖长短链、竖横屏、登录限制和不同长度。运行固定版本 yt-dlp，记录是否需要会话、失败类型、下载耗时与字节量；用 ffprobe 确认得到真实视频。抖音和小红书先验证高风险登录与页面解析场景，B 站同时确认单 P 行为。

用少量自制图片验证 DeepSeek OCR、Kimi 单图与有序多图、请求体大小、JSON 输出、结束状态及用量字段。核实 Base URL 的 `/v1` 拼接方式和网关限制，确定配置默认值。模型探测使用实际所属用户凭证，记录真实成本。

完成条件：三个平台分别有成功样本和可行动的失败说明；模型真实接收图片并能区分顺序。若必须依赖浏览器，先实现最小平台会话路径，再进入完整工作台开发。不能因一个平台通过就宣告三平台支持。

### 第二阶段 建立持久化下载任务

新增 core 契约、迁移、分析 repository、私有存储接口、创建与查询路由、专用队列和 Worker。实现平台适配、受控出口、限额下载、时长复核、取消及清理。补 Docker 与开发启动脚本。

完成条件：单链接可下载并探测，超时长或超大小能及时结束；服务重启、重复点击和 Redis 暂时故障不产生重复业务任务；用户不能读取他人的任务与文件。

### 第三阶段 实现抽帧与字幕提取

先用合成视频验证时间映射、周期采样、场景变化和局部文字变化，再接 DeepSeek。保存逐帧原文、合并文字、补采原因与预算消耗。实现人工校对和修订。

完成条件：相同背景上的字幕切换仍能进入识别；价格和否定词变化不被去重吞掉；可变帧率与旋转视频的帧时间、显示方向正确；预算不足时返回部分结果与覆盖提示。

### 第四阶段 实现 Kimi 观察与摘要

按时间分组图片，生成带证据的画面观察，再结合 OCR 生成摘要与营销要点。加入引用检查、空值、截断、拒答和未知调用处理。摘要失败时保留字幕；修订文字后只重新生成依赖该修订的结果。

完成条件：摘要可回到对应帧或文字；无声音输入时不会输出“实际口播”；不同批次的事件顺序不被打乱；调用中断不会自动重复收费。

### 第五阶段 接入营销工作台

新增“视频链接”入口，展示下载、抽帧、字幕、画面理解和综合进度。提供历史、取消、继续、证据预览、字幕校对及分别复制字幕或摘要。选用到现有改写流程时保留版本和用户确认步骤。

完成条件：刷新后恢复任务和结果，多标签页编辑产生版本冲突提示，切换账号不残留其他用户结果；同时验证中文、英文和暗色主题。生成视频仍走原有分镜确认流程。

### 第六阶段 真链回归与小规模上线

建立版本化评测集，每平台至少 10 条有效视频，并加入需要登录、失效链接、超长、非视频和下载中断等失败样本。固定标注与模型参数，记录下载成功率、字幕漏检、关键字段错误、摘要事实错误、实际费用及 P50/P95 延迟。

完成条件：三平台有效样本全部逐条验收；失败原因明确且可恢复；数据隔离、取消、未知请求保护和费用去重通过。若某平台持续受挑战页阻断，应明确受支持的会话条件并继续解决，不能用模拟测试替代实际交付。

## 验收清单与评测方式

| 维度 | 核对重点 |
| --- | --- |
| 下载 | 三平台长短链、B 站单 P、失效地址、重新解析、登录过期、真实 MP4 字节、流式大小限制 |
| 采样 | 固定背景换字幕、快切、300 毫秒文字、长镜头、首尾 CTA、可变帧率、旋转和起始时间偏移 |
| 字幕 | 分开统计采样漏检与 OCR 识别错误；价格、品名、否定词人工标注核对；重复出现的文字保留时间顺序 |
| 摘要 | 每条事实有帧或文字引用；推断单列；没有字幕的片段不编造口播；跨批次顺序正确 |
| 恢复 | 各阶段杀进程、Redis 投递失败、网络断开、模型提交未知、用户取消、同一请求重复投递 |
| 安全 | 越权读取、短链重定向到内网、DNS 重绑定、下载器旁路、路径穿越、超像素媒体和恶意清单 |
| 交互 | 刷新恢复、部分成果、校对版本、草稿冲突、中英文及暗色主题 |
| 成本 | 原图/裁剪/重叠帧都计入预算；网关用量可追踪；未知费用不归零；已完成批次不重复计量 |

采样召回率用“有候选帧命中可见区间的标注文字条数 / 标注文字总条数”衡量；OCR 准确率在已经命中的清晰文字上计算，避免把两类错误混在一起。初始目标可设清晰常驻字幕字符准确率不低于 95%、关键价格和否定词无未提示的误读、摘要无无依据事实；这些是上线目标，需在真实样本中验证。

保留普通样本与快速字幕压力样本的分项结果。压力样本无法覆盖时必须输出限制，不把标记不确定算作“完整提取成功”。原始视频理解作为后续候选时，使用同一套标注比较字幕召回、事实准确率、时间定位、延迟与费用，再决定是否增加该路径。

单位任务成本按所有 OCR 图片调用、Kimi 分段调用及综合调用的真实输入输出用量累加，另计下载流量、存储和计算。不写死单条视频价格，也不预设抽帧一定比直接视频便宜。先通过更合适的帧选择和已完成步骤复用降低重复输入，再调整模型。

当前已新增 Responses、下载/抽帧与模型编排、PG 任务/计量、独立 Worker 和工作台。已对用户提供的一条小红书素材完成真实下载、抽帧、4 次初探与 85 次完整模型调用；保留 3 帧 OCR 缺口，实际用量、语义问题及修复范围见实现文档。单样本测试与后续批量质量验收分别记录，上述参数与质量目标仍需随阶段一和第六阶段的结果更新。
